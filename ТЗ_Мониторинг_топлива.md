# Техническое задание: региональный мониторинг цен на топливо

Версия 2.2 · 24.10.2026 · конкурсный MVP с автономным сервисом данных на существующей VPN VPS; полный доступный региональный охват источника.

Принятые изменения: отдельный backend с API и сборщиком по расписанию; SQLite вместо PostgreSQL; Python venv и systemd вместо новых контейнеров проекта; frontend на Vercel; резервный снимок для демонстрации; сдача через Яндекс Форму — файл отчёта и публичная ссылка на сервис. Docker и VPN пользователя продолжают работать в существующей конфигурации.

## 1. Продукт и результат

**Пользователь:** владелец или управляющий фермерского хозяйства, специалист по снабжению.

**Задача:** оценить изменение региональных цен, сравнить регионы и рассчитать ориентировочный бюджет заправки техники перед закупкой.

**Результат разработки:** работающий адаптивный веб-прототип с реальными историческими данными и автономным сервисом их обновления. Фильтры, графики, сравнение и калькулятор выполняют реальные операции. Пользователю регистрация не требуется. Фронтенд получает данные через API; сборщик работает независимо от посещений сайта.

**Ограничение данных:** средние потребительские цены используются как ориентир бюджета. Сервис не выдаёт их за цены конкретных АЗС, оптовые предложения или гарантированную стоимость закупки. Для расчёта по предложению поставщика пользователь может ввести собственную цену.

**Ключевой сценарий:** регион → дизельное топливо → период → динамика → сравнение с другим регионом → объём заправки техники → бюджет и разница расходов.

## 2. Границы MVP

### P0 — обязательно к сдаче

- Все регионы, представленные в региональной таблице источника; в проверенном наборе — 85 субъектов. Справочник доступен через API. Федеральные округа, среднее по РФ и перекрывающиеся агрегаты исключены. Прежние ID шести пилотных регионов сохраняются.
- Для Архангельской области используются цены без Ненецкого АО, для Тюменской области — без ХМАО и ЯНАО; автономные округа доступны отдельно. Территориальный срез цены явно указывается в метаданных `price_area`.
- Отсутствующие в источнике территории/ряды не получают выдуманных цен: интерфейс показывает недоступность. Полный охват источника не означает наличие данных вне его публикаций.
- ДТ, АИ-92, АИ-95. Добавлять тип топлива можно только при наличии исходных данных.
- Для демонстрационного набора — минимум 13 последовательных недельных дат наблюдений, покрывающих 12 недель. Пропуски сохраняются как пропуски; полнота проверяется до фиксации набора.
- Фильтры региона, топлива, периода; просмотр динамики; сравнение 2–3 регионов.
- Калькулятор заправки с ценой из статистики или собственной ценой.
- Дата наблюдения, источник и состояние свежести данных.
- Состояния загрузки, ошибки, отсутствия и неполноты данных.
- Десктопный и мобильный интерфейсы.
- Автономная ежедневная проверка новых публикаций; повторяемая первоначальная загрузка истории.
- Отдельный сервис данных с публичным read-only API, SQLite и журналом запусков сборщика.
- Автоматическая публикация прошедших проверки данных; изоляция подозрительных изменений до ручного решения.
- Резервный проверенный снимок для работы интерфейса при недоступности API, с явной отметкой режима.
- Публичный frontend на Vercel, доступный без регистрации, и файл отчёта для прикрепления в Яндекс Форме.
- Воспроизводимое развёртывание, резервное копирование и инструкция запуска.

Список выше — граница разработки, а не заявление о том, что данные уже собраны. При недостатке истории сначала расширяется поиск публикаций; недостающие значения не генерируются.

### P1 — после завершения P0

- План сельхозработ: площадь × расход в л/га либо моточасы × расход в л/ч.
- Сценарии изменения цены на заданный пользователем процент.
- Выгрузка таблицы сравнения в CSV.
- Расширение географии при подтверждённой полноте данных.

### Вне MVP

- Прогнозирование цен и рекомендации о моменте закупки.
- Каталог поставщиков, карта АЗС, поиск самого дешёвого предложения.
- Заявки на поставку, оплата, личный кабинет, уведомления.
- Автоматическое назначение расхода топлива по модели техники.
- Смешение розничных и оптовых рядов; пересчёт руб./т в руб./л без исходной плотности.
- Разделение ДТ на летнее, зимнее и арктическое при отсутствии такого разреза в источнике.

## 3. Источники и правила данных

### 3.1. Основной источник

Росстат, еженедельные публикации «О потребительских ценах на нефтепродукты». Используется таблица **средних потребительских цен по субъектам РФ в рублях за литр**.

- [Каталог публикаций](https://rosstat.gov.ru/compendium/document/50798).
- [Пример недельной публикации на 12.10.2026](https://rosstat.gov.ru/storage/mediabank/159_14-10-2026.html).

Наличие публикаций и нужного типа региональной таблицы подтверждено по открытым материалам. Полноту конкретной истории и корректность каждой строки необходимо проверить при подготовке набора. Доступность HTML не гарантируется; исходные документы сохраняются в постоянном каталоге backend и включаются в резервную копию.

**В MVP используется только недельный ряд.** Месячные значения не подмешиваются в него. Индексы изменения цен не используются вместо абсолютных цен. Среднее по РФ, если будет добавлено, берётся из источника, а не вычисляется простым средним субъектов.

### 3.2. Правила нормализации

- Внутренние идентификаторы регионов стабильны; названия и варианты написания сопоставляются через явный справочник.
- Строки федеральных округов, РФ и региональных агрегатов не попадают в список субъектов как самостоятельные регионы.
- Топливо приводится к `diesel`, `ai92`, `ai95`.
- Цена хранится целым числом копеек за литр; валюта — RUB; единица — литр.
- Запятая в числе, неразрывные пробелы, объединённые заголовки и обозначения отсутствующих значений обрабатываются явно.
- Отсутствующая цена — `null`/нет наблюдения; никогда не `0`.
- `observation_date` — календарная дата регистрации цены, не дата публикации и не время скачивания.
- Повторный импорт одинакового документа не создаёт дубликатов.
- Исправленная публикация создаёт новую ревизию; изменение цены показывается в отчёте импорта и требует проверки перед выпуском.
- Резкий скачок цены помечается для проверки, но не удаляется автоматически. Порог — настраиваемый параметр проекта, не свойство официальной методологии.

### 3.3. Свежесть

Хранить отдельно дату наблюдения, дату публикации и время загрузки. Возраст данных для свежести считается от последнего наблюдения по региону и топливу, а не от конца исторического периода пользователя.

- До 14 календарных дней включительно — обычное состояние.
- Более 14 дней — «Данные требуют обновления» с датой последнего наблюдения.
- 14 дней — продуктовый порог MVP; он настраивается.
- Исторический период помечается как исторический даже при свежем наборе в целом.
- Ошибка обновления не удаляет последний корректный набор.
- В интерфейсе различаются «Источник проверен», «Набор опубликован» и «Цена зарегистрирована». Успешная проверка без новых публикаций обновляет только первую отметку.
- Если сборщик не завершил успешную проверку более 48 часов, показывается предупреждение о проверке источника, даже если сами недельные цены ещё свежие. Это отдельный настраиваемый эксплуатационный порог.

## 4. Интерфейс и функциональные требования

### 4.1. Общие фильтры

**FR-01. Регион:** поиск по названию, одиночный базовый регион, только доступные регионы. При первом открытии — Приморский край. Автоопределение геолокации не требуется.

**FR-02. Топливо:** ДТ по умолчанию; переключение на АИ-92 или АИ-95. Тип топлива сохраняется при переходе между представлениями.

**FR-03. Период:** по умолчанию последние 4 недели относительно последней даты набора; быстрый выбор 4/8/12 недель и две календарные даты. Границы включительны. Начало не позже конца; выбор вне загруженного диапазона блокируется. Показываются фактические даты доступных наблюдений.

**FR-04. Сохранение выбора:** регион, топливо, период и сравниваемые регионы хранятся в URL. Обновление страницы и переход по ссылке восстанавливают выбор. Некорректные параметры заменяются допустимыми с понятным уведомлением. Дополнительный параметр `dataset_version` фиксирует версию для воспроизводимого просмотра. Без него при открытии берётся текущая опубликованная версия. Недоступную явно выбранную версию нельзя молча заменять другой.

### 4.2. Обзор региона

**FR-05. Показатели:** цена на последнюю доступную дату внутри периода; изменение к первой доступной дате периода в руб./л и процентах; минимум и максимум наблюдавшихся цен. Для изменения показывать обе фактические даты. При одной точке изменение не рассчитывать.

**FR-06. График:** X — реальные даты наблюдений; Y — руб./л. Подсказка содержит регион, топливо, дату и цену. Пропуски отображаются разрывами. Недельные данные не интерполируются в ежедневные. При неполном ряде показывается отметка о пропусках.

**FR-07. Источник:** возле графика ссылка «О данных»; в ней метод использования, единицы, охват, диапазон истории и ссылки на публикации. Цена последнего наблюдения ведёт к своей публикации.

**FR-08. Передача в калькулятор:** кнопка «Рассчитать заправку» переносит регион, топливо и цену последнего наблюдения выбранного периода с датой и источником.

### 4.3. Сравнение регионов

**FR-09. Выбор:** базовый регион плюс максимум два дополнительных. Дубликаты запрещены. Все линии относятся к одному топливу и одному выбранному периоду.

**FR-10. Сопоставимость:** для числовой таблицы определить общие даты выбранных регионов внутри периода. Конечная дата — самая поздняя общая дата; начальная — самая ранняя. Показывать обе даты. Для динамики требуется минимум две общие даты. Для сравнения уровня цен достаточно одной общей даты.

Если общих дат нет — график доступных наблюдений можно показать, но таблица разницы и сравнение бюджета недоступны с объяснением. Если выбранный набор регионов изменился, общие даты пересчитываются.

**FR-11. Таблица:** регион; цена на общую конечную дату; разница с базовым регионом в руб./л и процентах; изменение между общей начальной и конечной датами. Заголовок явно указывает даты расчёта.

**FR-12. Интерпретация:** обозначать «разница по средним региональным ценам». Не называть её гарантированной экономией закупки. Доставка и условия поставщика не учтены.

### 4.4. Калькулятор заправки

**FR-13. Вход:** список строк техники. В строке — произвольное название, объём одной заправки в литрах, число одинаковых машин. Объём вводит пользователь; справочник баков и норм расхода не нужен. Можно добавить и удалить строку; максимум 20 строк.

Два режима объёма:

- «Заправка техники» — сумма строк `литры на машину × число машин`.
- «Готовый объём» — прямой ввод суммарного количества литров для расчёта партии.

Режимы взаимоисключающие: приложение не суммирует скрытые значения другого режима.

**FR-14. Источник цены:** «Средняя по региону» либо «Моя цена». Средняя — последнее наблюдение выбранного периода. Собственная цена вводится в руб./л и явно подписывается как пользовательская; она не записывается в статистику. Возврат к средней — отдельное доступное действие.

При изменении региона/топлива/периода средняя цена пересчитывается. В режиме собственной цены значение сохраняется, показывается уведомление о том, что оно применяется к новому выбору. Подпись региона не должна выдавать собственную цену за региональное наблюдение.

**FR-15. Результат:** общий объём, используемая цена, дата/происхождение цены, итоговая сумма. Подпись: «Ориентировочная стоимость топлива. Доставка и дополнительные условия закупки не учтены».

**FR-16. Исторический расчёт:** при выборе прошлого периода показывать «Расчёт по исторической цене на …». Предусмотреть действие «Перейти к последним данным».

**FR-17. Сравнение бюджета:** для одинакового объёма показывать стоимость по выбранным регионам на общей конечной дате. Для этой таблицы всегда используются статистические цены; собственная цена показывается отдельно и не подменяет их.

**FR-18. Проверка ввода:** литры и цена — положительные числа, до двух знаков после запятой; количество машин — целое положительное число. Принимать запятую и точку как десятичный разделитель. Пустое поле, отрицательное значение, ноль, бесконечность и неверный формат блокируют итог; ошибка возле поля. Не исправлять неверный ввод молча.

Предельные значения — явно заданная конфигурация с сообщением при превышении; расчёты выполняются безопасной десятичной арифметикой. В MVP: до 1 000 000 л на строку/прямой ввод, до 1 000 машин на строку, цена до 10 000 руб./л. Пределы технические, не рыночные оценки.

### 4.5. Состояния и адаптация

- Загрузка: скелетон; новые фильтры не сопровождаются старыми показателями без отметки загрузки. Незавершённый запрос старого выбора отменяется или его результат игнорируется.
- Нет данных: выбранные условия, причина, предложение расширить период или изменить регион.
- Одна точка: цена доступна, динамика недоступна.
- Пропуски: разрывы графика и предупреждение о неполном покрытии.
- Недоступность API: переключение всего экрана на резервный снимок с его датой и отметкой режима; при отсутствии нужных данных — объяснение и повторная попытка.
- Устаревший набор: последнее корректное наблюдение остаётся доступным с предупреждением.
- Мобильный экран от 360 px: фильтры и карточки в одну колонку; таблица прокручивается внутри блока, не вся страница.
- Линии различаются цветом и подписью; знак изменения передаётся текстом, не только цветом. Поля имеют подписи, интерфейс доступен с клавиатуры.

### 4.6. Сервис данных

**FR-19. Автономный сбор:** ежедневная задача проверяет новые и изменённые публикации. Есть отдельный режим первичной загрузки истории. Запуск API или открытие сайта не запускают сбор.

**FR-20. Контроль качества:** обычные новые наблюдения публикуются автоматически после проверок. Изменения ранее опубликованных цен, неизвестная структура, конфликты и аномалии переводят кандидата в `needs_review`. Публичный набор продолжает работать. Решение оператора и его причина сохраняются; административный интерфейс MVP — CLI, а не публичная веб-страница.

**FR-21. API:** отдаёт справочники, историю и сравнение. Результаты содержат версию, даты и ссылки на источники. Публичных методов изменения цен нет.

**FR-22. Согласованность:** все данные одного экрана относятся к одной опубликованной версии. Новое поступление данных не меняет цифры посреди текущего просмотра; интерфейс предлагает обновить набор.

**FR-23. Наблюдаемость:** фиксируются начало/конец, состояние и статистика каждого запуска, ошибки и количество строк. Наличие ошибок видно оператору в журнале и пользователю через нейтральный статус актуальности без внутренних трассировок.

**FR-24. Резервный режим:** при недоступности API фронтенд использует только заранее подготовленный проверенный снимок. Его источники и версия сохранены; режим явно обозначен. Подмена отдельных ответов данными другой версии запрещена.

## 5. Формулы и расчётные правила

Обозначения: `P0`, `P1` — цены на начальную и конечную фактические даты; `PA`, `PB` — цены регионов A и B на общую дату; `V` — литры.

```text
Изменение цены:          ΔP = P1 − P0
Изменение, %:            ΔP% = (P1 − P0) / P0 × 100
Разница B относительно A: ΔBA = PB − PA
Разница, % к A:          ΔBA% = (PB − PA) / PA × 100
Общий объём техники:    V = Σ(литры_i × количество_i)
Стоимость:              C = V × P
Разница бюджета B и A:  ΔC = round(V × PB, 2) − round(V × PA, 2)
```

- Нулевая/отсутствующая базовая цена исключает вычисление процентов; показывается «Нет данных».
- Изменение собственно цены, вычисленное приложением, не подписывается как официальный индекс Росстата.
- Денежные вычисления: decimal либо целочисленные масштабированные величины с точным округлением; не полагаться на двоичное округление `Number`.
- Округлять конечную денежную сумму до копейки по правилу HALF_UP. Общий объём считать точно; не округлять промежуточные произведения по строкам.
- Проценты отображать с двумя знаками; точные исходные цены не изменять.

**Проверочный пример, все значения условные:** 3 машины по 200 л → 600 л. При 80 руб./л стоимость 48 000 руб.; при 82 руб./л — 49 200 руб.; разница — 1 200 руб. Изменение 80 → 82 равно +2 руб./л и +2,50%.

**P1, план работ:** `V = площадь_га × расход_л_на_га` либо `V = моточасы × расход_л_в_час`. Режим выбирается явно; нормы вводит пользователь. Сценарная цена `P_s = P × (1 + r / 100)`; отрицательная итоговая цена запрещена. Показатель `r` — предположение пользователя, не прогноз сервиса.

- **Резервный адаптер frontend:** реализует тот же контракт чтения над проверенным снимком. Для него нужны те же контрольные примеры сравнения, что для backend; его результаты сверяются с API.

### 6.3. Размещение и эксплуатация

- Frontend: публичный production-адрес Vercel. Проверить отсутствие Vercel Authentication для адреса сдачи.
- Backend: существующая VPN VPS пользователя. Python venv, один процесс Uvicorn без dev-reload под systemd; сборщик — отдельный oneshot service. SQLite обслуживается внутри процессов приложения. API работает постоянно.
- По переданной пользователем диагностике: 1 vCPU, 956 МиБ RAM, ранее 487 МиБ available и swap отсутствует; корневой раздел 15 ГБ, свободно 6,5 ГБ. В отдельном срезе контейнеры `amnezia-xray`, `amnezia-awg2`, `3x-ui` использовали суммарно около 109 МиБ RAM. Эти срезы не синхронны и не доказывают запас при пиковой VPN-нагрузке; измерения повторить перед выкладкой.
- TCP 80/443 в переданном выводе не слушаются, UFW неактивен. Это не доказывает доступность портов снаружи или отсутствие других firewall-правил. HTTPS-имя, DNS и внешняя доступность остаются задачами этапа развёртывания.
- Существующие VPN-контейнеры, Docker, маршрутизация и firewall не переустанавливаются и не перезапускаются ради проекта. UFW автоматически не включается. Перед сетевыми изменениями сохранить текущую конфигурацию, предусмотреть откат и проверить VPN до/после; рабочий SSH сохраняется.
- Расписание: ежедневно в 07:00 UTC, то есть 18:00 Asia/Vladivostok. Время задаётся явно в UTC; пропущенный из-за остановки сервера запуск выполняется после восстановления.
- Внутрипроцессный планировщик API не используется: перезапуск или увеличение числа API-процессов не должны создавать дубли задач.
- Выделить непривилегированного пользователя приложения и каталоги `/opt/fuel-monitor` для кода/venv, `/var/lib/fuel-monitor` для БД/оригиналов/блокировки. Права не открывать всем пользователям. API открывает SQLite через URI `mode=ro` и `query_only=ON`; сборщик и административный CLI — с записью. Это настройки соединений, не серверные роли PostgreSQL. Проверить доступ к WAL/SHM; `immutable=1` для изменяемой БД не использовать. Миграции выполняются до запуска приложения и под общей блокировкой записи.
- Публичен только HTTPS API. CORS разрешает production frontend и локальную разработку; preview-домены добавляются явно. CORS не считается механизмом авторизации.
- Все публичные методы — чтение; управление импортом/одобрением/откатом выполняется CLI с доступом оператора к серверу.
- Серверная конфигурация и возможные секреты инфраструктуры — файл окружения с ограниченными правами, вне Git. В `VITE_API_BASE_URL` хранится только публичный адрес API. У SQLite нет сетевого пароля; доступ определяется файлами и приложением.
- БД, WAL/SHM и оригиналы — постоянные файлы на локальном диске VPS; обновление кода их не перезаписывает. Хранение в сетевой папке или на ФС Vercel не используется.
- Ежедневная согласованная копия через SQLite Online Backup API (`sqlite3.Connection.backup`) плюс оригиналы; хранить минимум 7 последних копий. Обычным копированием одного живого `.sqlite` файла резерв не делать. До сдачи проверить восстановление в отдельной БД и `integrity_check`; одну копию разместить вне VPS. Целевой RPO — 24 часа, RTO — 4 часа; это проверяемые цели, а не уже достигнутые показатели.

### 6.3.1. Ресурсный бюджет и совместная работа с VPN

- Цель проекта по диску — до 1,5 ГБ с venv, данными и локальными резервами. Сборка frontend выполняется вне VPS. Не хранить на сервере бесконечную историю окружений и сборок.
- Предварительные оценки RSS: API 100–200 МиБ, сборщик 100–200 МиБ на время запуска. Это не лимиты и не измерения готового кода. Прокси и служебные процессы также входят в измеряемый общий бюджет.
- Начальная конфигурация ограничений systemd для испытаний: API `MemoryMax=192M`, `CPUQuota=50%`; сборщик `MemoryMax=160M`, `CPUQuota=20%`, `Nice=10`. Проверить поддержку контроллеров и фактическое применение на VPS. Значения корректируются по замерам; лимит памяти может завершить процесс, а не гарантировать его работоспособность.
- Парсить по одному документу, без headless-браузера/OCR, сетевой параллелизм — 1. Первую загрузку истории выполнять вне активной VPN-нагрузки. Не запускать несколько сборщиков/миграций/операций публикации одновременно.
- Перед записью новых документов/версии проверить не менее 2 ГБ свободного диска. При меньшем запасе остановить обновление с кодом `LOW_DISK`, сохранить старый набор и записать причину. БД и документы автоматически не удалять.
- Логи самого проекта ограничить ротацией до 100 МиБ, не менять глобальные политики журналирования VPN. Контролировать размер оригиналов, резервов и WAL; checkpoint выполнять с ограниченным ожиданием и без долгих читающих транзакций.
- Испытать одновременно активный VPN, API с 10 пользователями и сборщик. Зафиксировать RAM available, пик RSS, CPU, время API, ошибки, перезапуски/OOM и доступность VPN. Критерии: нет OOM, обрывов VPN и нарушений целевого времени API; доступная память не опускается ниже 100 МиБ. Пороги — проектные цели приёмки, не уже подтверждённый запас.
- Если совместный тест не проходит, резервный вариант — вынести сборщик на локальный компьютер с контролируемой публикацией результата либо увеличить RAM. Не снимать ограничения и не менять VPN молча. Добавление swap — отдельная эксплуатационная настройка после оценки, не замена RAM и не обязательный шаг.

### 6.3.2. Особенности SQLite

- Включить WAL, `foreign_keys=ON` для каждого соединения и `busy_timeout=5000`; выполнять короткие транзакции. Режим журнала настраивается писателем при инициализации, не read-only API.
- Запись только одним процессом одновременно: общий файловый lock для сборщика, публикации, отката, backup и миграций. Для API — небольшой пул соединений, без долгих транзакций; таблицы и источники читаются согласованно.
- Сеть/скачивание/разбор выполняются вне транзакции записи. Активный указатель меняется в короткой транзакции вместе с завершением версии. При конфликте блокировки — ограниченное ожидание/повтор, затем сохранение старой версии и отчёт ошибки.
- Изменения схемы выполнять совместимыми миграциями; при необходимости короткой остановки останавливается только сервис проекта. VPN-сервисы не затрагиваются.

### 6.4. Модель данных и выпуск версии

| Сущность | Основные поля и ограничения |
|---|---|
| Region | `id`, `name`, `source_name`, алиасы |
| FuelType | `id`, `name` |
| SourceDocument | `id`, `url`, `published_date`, `retrieved_at`, `sha256`, `storage_path`; уникальная ревизия по URL и хешу |
| ImportRun | `id`, `mode`, `started_at`, `finished_at`, `status`, счётчики, код ошибки; `mode=bootstrap/incremental` |
| DatasetVersion | `id`, `schema_version`, `created_at`, `published_at`, `state`, `import_run_id`, покрытие, отчёт проверок |
| Observation | `dataset_version`, `region_id`, `fuel_type`, `observation_date`, `price_kopecks`, `source_id`, `source_row` |
| DatasetState | одна строка с `active_version_id`; меняется только после успешного выпуска |
| ReviewDecision | версия, решение, причина, время, идентификатор оператора |

- Уникальность наблюдения: `(dataset_version, region_id, fuel_type, observation_date)`; `price_kopecks > 0`. Индекс чтения совпадает с этим составом.
- Отсутствие наблюдения не превращается в нулевую цену; ожидаемые даты и покрытие хранятся в метаданных версии и возвращаются API для отображения разрывов.
- Новая версия содержит полную историю текущего охвата: предыдущие данные плюс проверенные изменения. Полная копия набора допустима для объёма MVP и упрощает воспроизводимость.
- Состояния версии: `candidate → published` либо `candidate → needs_review → published/rejected`. Опубликованная версия неизменяема. Старые опубликованные версии доступны до завершения оценки конкурса.
- Обычное обновление публикуется автоматически. Конфликт, подозрительное изменение и исправление старой цены требуют решения оператора; все блокирующие проверки должны быть устранены или документированно разрешены до публикации.
- Ручное решение может принять подтверждённый по оригиналу скачок/исправление. Оно не отменяет обязательные инварианты схемы, уникальности, положительной цены, известной единицы и наличия источника.
- Транзакция выпуска завершает запись наблюдений, помечает версию опубликованной и меняет `active_version_id`. Читатель видит целиком старую или целиком новую версию.
- Откат меняет указатель на ранее опубликованную версию с записью причины. История не удаляется.
- Неизменившиеся документы не создают новые наблюдения и новую версию. Успешная проверка без новых данных фиксируется в `ImportRun`.
- Исходный документ сохраняется до записи ссылок на него; путь строится по хешу, запись файла атомарная. Несвязанные файлы после сбоя можно очистить отдельной командой.

### 6.5. REST API

Базовый путь `/api/v1`. Параметры и JSON фиксируются в OpenAPI, опубликованном вместе с API. Все даты наблюдений — `YYYY-MM-DD`; служебные времена — ISO 8601 UTC. Цены — целые копейки за литр. Денежные/процентные агрегаты с дробной частью передаются десятичными строками.

| Метод | Параметры | Результат |
|---|---|---|
| `GET /api/v1/meta` | необязательный `dataset_version` | Справочники, покрытие по региону/топливу, ожидаемые даты, источники, текущая и выбранная версии, статус обновления |
| `GET /api/v1/prices` | `region`, `fuel`, `from`, `to`, `dataset_version` | Наблюдения, первая/последняя фактические даты, min/max, изменение цены, полнота |
| `GET /api/v1/comparison` | повторяемый `regions` — 2–3 значения, `base_region`, `fuel`, `from`, `to`, `dataset_version` | Ряды для графика, общие даты, цены и разницы; `comparable` и причина отсутствия сравнения |
| `GET /health/live` | нет | Жив ли процесс API; без внутренних подробностей |
| `GET /health/ready` | нет | Доступна ли БД и существует ли опубликованная версия; 200 или 503 |

Для `/prices` и `/comparison` версия обязательна. `meta` без версии разрешает текущую активную, после чего frontend закрепляет её во всех запросах. Если `dataset_version` указан в пользовательской ссылке, сначала запрашивается `meta` именно этой версии.

**Параметры:** `from ≤ to`; диапазон не более 366 календарных дней; топливо из справочника; сравниваемые регионы уникальны, базовый входит в их список. Неизвестные идентификаторы/версии — 404; неправильный формат/enum/диапазон — 422. Регион без данных по заданному периоду — 200 с пустым массивом; неполный ряд — 200 с предупреждением.

**Общие метаданные:** `schema_version`, `dataset_version`, `generated_at`, запрошенный и фактический периоды, `warnings`. В `meta` дополнительно: `latest_observation_date` по рядам, `last_successful_check_at`, `last_published_at`, публичный код состояния обновления. Пустой результат имеет `actual_period: null`; неизвестные агрегаты — `null`, не ноль.

Пример `/prices`: условные значения демонстрируют контракт, не статистику.

```json
{
  "schema_version": "1",
  "dataset_version": "dataset-example-001",
  "generated_at": "2026-10-23T07:10:00Z",
  "region_id": "primorsky_krai",
  "fuel_type": "diesel",
  "requested_period": {"from": "2026-10-01", "to": "2026-10-19"},
  "actual_period": {"from": "2026-10-12", "to": "2026-10-19"},
  "observations": [
    {"date": "2026-10-12", "price_kopecks": 8000, "source_id": "source-example-1"},
    {"date": "2026-10-19", "price_kopecks": 8200, "source_id": "source-example-2"}
  ],
  "summary": {
    "latest_price_kopecks": 8200,
    "min_price_kopecks": 8000,
    "max_price_kopecks": 8200,
    "change_kopecks": 200,
    "change_percent": "2.50"
  },
  "warnings": ["INCOMPLETE_PERIOD"]
}
```

В `/comparison` результат включает `common_dates`, `comparison_start`, `comparison_end`, `comparable` и `reason`; разница B−A следует формулам раздела 5. При одной общей дате доступно сравнение уровней, изменение за период — `null`.

**Ответы:** 200 — успешный результат; 304 — при реализованном условном GET; 404 — неизвестная сущность/версия; 422 — неверный запрос; 429 — ограничение частоты; 503 — БД/опубликованный набор недоступны; 500 — внутренняя ошибка. Ответ ошибки: `error.code`, `error.message`, `request_id`; трассировка и учётные данные не возвращаются.

**Ограничения и кэш:** ограничить публичное чтение middleware API, начальная настройка — 60 запросов в минуту на IP с кратким допустимым всплеском; 429 содержит `Retry-After`. Для одного процесса достаточно ограниченного по размеру in-memory счётчика с TTL; Redis и модуль rate limit для Caddy не требуются. Адрес клиента принимать только от доверенного локального proxy. Для ответов цены/сравнения использовать короткий HTTP-кэш до 60 с; ключ включает полный запрос и версию. `meta` кэшируется не более 60 с; healthcheck — `no-store`. Отдельный сервер кэша не нужен.

### 6.6. Работа frontend с версиями и резервом

1. Прочитать параметры URL и получить `meta`.
2. Закрепить версию в состоянии и ключах TanStack Query: версия, регион/регионы, топливо, даты.
3. Параллельно загрузить необходимые данные; отменять запросы устаревшего выбора. Не показывать цену предыдущего региона под заголовком нового.
4. Проверять `schema_version` и совпадение `dataset_version` в каждом ответе. Несовпадение — ошибка, а не повод объединять данные.
5. Проверять наличие новой активной версии при возврате на вкладку, не чаще раза в 5 минут. Предлагать «Доступны новые данные — обновить». При принятии обновить весь экран согласованно.
6. При тайм-ауте/сетевой ошибке/503 сделать не более двух повторов, затем переключить весь источник данных на резервный адаптер. Для начального подключения — до 2 с на попытку, задержки 0,3 и 0,6 с, общий бюджет ожидания до 7 с; после него запросы отменяются. 404, 422 и ошибки схемы не маскировать автоматическим резервом; для них показать причину.
7. Резерв — проверенный экспорт опубликованной версии, включённый в сборку Vercel: метаданные, наблюдения, источники и ожидаемые даты. Показывать постоянную отметку «Резервные данные на …», возраст и версию. Не брать часть показателей из API, часть из резерва.
8. Если в URL закреплена другая версия, предложить явное переключение на резервную с изменением URL; автоматически подменять закреплённую версию нельзя.
9. Возвращаться к API только действием «Повторить подключение» с обновлением всего экрана. Нет нужных данных в резерве — обычное состояние отсутствия данных.

## 7. Пайплайн работы

### 7.1. Путь пользователя

1. Открывает приложение; frontend получает метаданные и закрепляет версию. По умолчанию — Приморский край, ДТ, последние 4 недели.
2. Выбирает регион, топливо и период; API возвращает историю и агрегаты одной версии.
3. Добавляет регион для сравнения; API определяет общие даты и разницу цен.
4. Открывает калькулятор; параметры и цена с датой/источником перенесены автоматически.
5. Вводит литры/машины либо готовый объём; frontend точно рассчитывает бюджет.
6. При необходимости вводит цену поставщика; происхождение меняется на «Моя цена».
7. Открывает источник или копирует ссылку с фильтрами и версией.

### 7.2. Первичная загрузка истории

1. Установить справочники регионов и топлива, настроить подключение к БД и каталог оригиналов.
2. Найти публикации за нужный период по реальным ссылкам каталога. Не конструировать URL документов по предполагаемому шаблону.
3. Скачать, сохранить и разобрать документы. В MVP автоматический парсер поддерживает HTML; PDF используется для ручной сверки. При отсутствии машиночитаемой таблицы отметить документ для разбора, не подключать незаметно OCR.
4. Собрать исходную версию для всех регионов источника (в текущем наборе 85), 3 видов топлива и 13 недельных дат. Сформировать отчёт полноты и список пропусков. При расширении географии повторно обработать всю выбранную историю, а не только последние 8 недель ежедневной проверки.
5. Проверить минимум 10% записей, не менее 20, с охватом всех регионов и видов топлива; все аномалии проверить отдельно.
6. Утвердить первую версию, включить публичный API, экспортировать резерв и включить ежедневный таймер.

### 7.3. Ежедневный автономный сбор

1. Таймер запускает oneshot service из venv. Сборщик получает неблокирующий файловый lock через `flock` на `/var/lib/fuel-monitor/collector.lock`; при занятости пишет `skipped_locked` в журнал и завершается без записи в БД. Дескриптор удерживается до конца запуска и освобождается при завершении процесса. Сам lock-файл во время работы не удаляется. Все команды, меняющие БД, используют ту же блокировку.
2. Создать `ImportRun`. Найти новые URL в каталоге и повторно проверить документы последних 8 недель на изменения. Полный повторный проход истории — отдельная команда перед сдачей и по требованию оператора.
3. Проверить свободное место и скачать документы по HTTPS. По прямому решению пользователя для разрешённых доменов Росстата допускается отключённая проверка сертификата через `FUEL_ROSSTAT_VERIFY_TLS=false`; в журнале и метаданных этот режим отражается явно. Исключение не является глобальным и не применяется к произвольным адресам. Ограничение доменов проверяется до каждого запроса и redirect. Документы обрабатываются последовательно, лимит документа — 10 МБ, общий срок запуска — до 15 минут. Файл больше лимита/парсер вне ресурсного бюджета — ошибка для разбора, а не снятие ограничений сервера.
4. Тайм-аут запроса — 30 с; максимум 3 попытки с увеличением задержки и jitter. Повторять сетевые ошибки, 429 с учётом `Retry-After` и временные 5xx. 404, неподдерживаемый формат и структурная ошибка идут в отчёт. Настройка TLS не отменяет проверки URL, размера и структуры документа; защиту сайта не обходить.
5. Сохранить документ и SHA-256. Тот же URL и хеш — пропуск повторного разбора; изменившийся документ — новая ревизия.
6. Найти таблицу по заголовкам и единицам, нормализовать регион/топливо/дату/цену. Проверить структуру, уникальность, положительность, даты, покрытие и изменения относительно активной версии.
7. Структурная ошибка, конфликт, исправление прежней цены или скачок выше порога переводят кандидата в `needs_review`. Начальный порог скачка — более 10% между соседними недельными наблюдениями; он конфигурируется. Интервал больше недели помечается отдельно, порог не пересчитывается как прогноз.
8. Если ошибок нет и есть новые данные — опубликовать версию транзакцией. Если новых данных нет — `no_changes` без новой версии. Если хотя бы один документ обязательной проверяемой области не удалось обработать — `partial_failure`, кандидат в этом запуске не публикуется; исходные файлы сохраняются для повтора.
9. Завершить отчёт, записать длительность, документы, строки, предупреждения и код результата. Проверка источника считается успешной только для полного прохода обязательной области. Публикация и ручное одобрение фиксируются отдельно.
10. Проверить API на контрольном запросе опубликованной версии. Ошибка источника сохраняет старый набор; ошибка после выпуска API расследуется по `request_id` и версии.

Состояния запуска: `running`, `published`, `no_changes`, `needs_review`, `partial_failure`, `failed`, `skipped_locked`. Отчёт кандидата не должен перезаписывать данные опубликованной версии. Зависший `running` после аварии помечается операторской/стартовой проверкой как прерванный только после подтверждения отсутствия активной блокировки.

### 7.4. Наблюдение, восстановление и резерв

- Структурированные логи JSON: `run_id`, этап, длительность, количество документов/строк, версия, код ошибки. Для API — `request_id`, маршрут, статус, время; без паролей и содержимого окружения.
- `meta` показывает время последней полной успешной проверки и последней публикации. При превышении порогов 48 часов/14 дней интерфейс показывает разные предупреждения.
- Оператор перед сдачей проверяет таймер, журнал, диск, резервную копию и публичную готовность API. Уведомления в мессенджер — P1, не обязательная зависимость.
- Команды CLI: `bootstrap`, `collect`, `review`, `publish`, `reject`, `rollback`, `export-snapshot`; точные аргументы описать в README. Каждое изменение активной версии журналируется.
- При восстановлении остановить только API и таймер проекта, получить lock, вернуть БД из согласованной копии и оригиналы, проверить `integrity_check`, запустить совместимые миграции при необходимости. После проверки версии и контрольных запросов вернуть API/таймер; VPN не останавливается.

### 7.5. Порядок разработки

| Этап | Работа | Условие завершения |
|---|---|---|
| 1. Проверка источника | Реальные документы, справочники, история, ограничения доступа | Доступен проверяемый набор и известны пропуски |
| 2. Основа backend | Venv, SQLite/WAL, миграции, модели версий, парсер | История воспроизводимо загружается и сохраняет источники |
| 3. API и доменная логика | Meta/prices/comparison, общие даты, агрегаты, OpenAPI | Контрактные тесты и контрольные примеры проходят |
| 4. Вертикальный срез | Frontend → API → БД; один регион, ДТ, график, калькулятор | Полный сценарий работает на реальных данных |
| 5. Автономность | Таймер, блокировка, повтор, кандидаты, атомарный выпуск, CLI | Повторный запуск безопасен; сбой не ломает чтение |
| 6. Полный P0 | Все фильтры/регионы, сравнение, URL, мобильная версия, резерв | Выполнены FR-01–FR-24 |
| 7. Развёртывание | Существующая VPN VPS: venv/systemd, лимиты, HTTPS; Vercel, CORS, backup/restore | Публичный сценарий и таймер проверены; VPN работает до/после и под совместной нагрузкой |
| 8. Приёмка | Данные, расчёты, API, отказные сценарии, производительность и совместная нагрузка VPN | Выполнены AC-01–AC-36; результаты записаны |
| 9. Сдача | Зафиксировать релиз, экспорт резерва, отчёт PDF, ссылка | Файл и сервис проверены в формате Яндекс Формы |

P1 начинается после приёмки P0. Статус «автономный сбор работает» подтверждается успешным запуском по расписанию на сервере, а не только локальным запуском команды. Развёртывание и покупка ресурсов выполняются отдельным этапом после подготовки кода и конфигурации.

### 8.2. Технические проверки

- Модульные тесты формул, округления, неполных рядов и выбора общих дат.
- Тесты парсера на сохранённых реальных документах: заголовки, пропуск, повтор, изменение структуры. Проверить объединённые ячейки, выбор правильной таблицы и исправленную публикацию.
- Интеграционные тесты API на файловой SQLite с тем же WAL-режимом, что в production: миграции, уникальность, статусы, версии, атомарность выпуска, отдельные процессы чтения/записи и блокировка сборщика. In-memory SQLite не заменяет эти проверки.
- Контрактные тесты OpenAPI и frontend-схем. Одинаковые фикстуры расчётов/сравнения для Python и резервного адаптера TypeScript.
- Отказные проверки: 429/5xx источника, тайм-аут, прерванный сбор, недоступная БД, остановленный API, устаревший резерв.
- Сквозной тест: фильтры → сравнение → калькулятор → собственная цена → возврат к статистике.
- Ручная сверка данных с исходными документами; синтаксическая корректность JSON её не заменяет.
- Сборка production-версии, запуск по инструкции на чистом окружении проекта, проверка HTTPS/CORS и восстановления резервной копии. Локальные проверки не заменяют проверку публичного развёртывания.

### 8.3. Нефункциональные цели

- После получения нужных данных локальная фильтрация резервного адаптера/отрисовка и расчёт — до 300 мс на обычном ноутбуке; измерить и записать фактическое окружение.
- Ответы `/prices` и `/comparison`: p95 серверного времени до 500 мс при 10 одновременных пользователях и наборе MVP; сетевую задержку измерять отдельно.
- Первый полезный экран с доступным API — до 3 с при холодной загрузке и профиле сети 10 Мбит/с, RTT 100 мс. Резервный экран при отказе API — не позднее 8 с; ограничить общий бюджет первоначальных попыток подключения. Измерить отдельно размеры frontend и резервного снимка.
- Современные Chrome/Edge и мобильный браузер; даты — русская локаль, цена — ₽/л.
- Недоступность Росстата не ломает чтение API; недоступность API допускает работу по явно отмеченному резервному снимку.
- Публичное приложение не требует аккаунта пользователя. Развёртывание backend использует серверные секреты; они не попадают в браузер, Git, логи и конкурсный файл.
- Подготовить healthcheck, журнал сборов, инструкцию отката и подтверждение реального запуска таймера. Высокая доступность нескольких серверов не входит в MVP; VPN, API и SQLite на одной VPS имеют общий риск отказа. Резерв frontend поддерживает просмотр сервиса, но не является резервом VPN.

## 9. Выпуск, файл решения и сдача через Яндекс Форму

### 9.1. Обязательные материалы для формы

1. **Файл с решённым заданием:** компактный отчёт 6–8 страниц, предпочтительно PDF. Перед оформлением проверить разрешённые расширения и размер вложения в самой форме. Если PDF не принимается, подготовить отчёт в разрешённом формате.
2. **Публичная ссылка на сервис:** постоянный production-адрес Vercel в поле ссылки и внутри файла; кликабельная ссылка на первой странице. Авторизация Vercel или приложения не требуется.

Файл отражает фактически реализованное решение: ТЗ само по себе не заменяет отчёт о готовой работе. Основная информация должна быть понятна без открытия сайта.

### 9.2. Содержание отчёта

| Часть | Содержание |
|---|---|
| 1. Продукт | Название, автор, проблема, аудитория, ссылка, версия релиза и дата данных |
| 2. Сценарий | От региона и динамики до расчёта заправки; реализованные возможности |
| 3. Экраны | Скриншоты обзора, сравнения и калькулятора с короткими пояснениями |
| 4. Данные | Источники, фактическая география/история, частота, пропуски, свежесть |
| 5. Расчёты | Формулы, воспроизводимый пример, допущения |
| 6. Архитектура | Frontend, API, БД, автономный сбор, проверка/публикация, резерв |
| 7. Результат | Что проверено, фактические показатели, ограничения и дальнейшие шаги |

Разделы могут объединяться на страницах. URL дублируется читаемым текстом; QR — необязательное дополнение. Не заявлять функции, охват и результаты, которые не подтверждены готовой версией.

### 9.3. Состав проекта для воспроизводимости

Сохранить в репозитории или приложениях проекта: frontend/backend, lock-файлы, units systemd API/сборщика/таймера с лимитами, конфигурацию HTTPS-прокси, миграции SQLite, OpenAPI, `.env.example` без значений секретов, README запуска/обновления/восстановления, тесты, отчёт импорта и приёмки, проверенный резервный JSON. Оригиналы и согласованная копия БД хранятся в подготовленном архиве/хранилище; их размещение в публичном Git не требуется. Ссылку на исходники добавлять по желанию, если это допускают правила. Конфигурация VPN, его ключи и пароли в материалы проекта не включаются.

### 9.4. Порядок выпуска

1. Завершить P0, тесты и сверку данных.
2. Зафиксировать состояние VPN/SSH, проверить RAM/диск/порты; развернуть venv/API/SQLite/таймер с лимитами. Проверить HTTPS, CORS, публичный API, реальный автоматический запуск и совместную нагрузку. Не включать UFW и не менять Docker/firewall вслепую.
3. Экспортировать опубликованную проверенную версию в резерв frontend.
4. Выпустить frontend на Vercel; проверить загрузку, фильтры, сравнение, калькулятор, прямые ссылки и резерв при отказе API.
5. Зафиксировать релиз, версию данных и ссылку для демонстрации. Разрешить дальнейшие проверенные обновления; ссылки с версией сохраняют воспроизводимость. Изменения кода после сдачи — только исправления с повторной проверкой.
6. Сделать скриншоты готовой сборки, оформить отчёт и проверить читаемость и ссылки в экспортированном файле.
7. Открыть сайт без аккаунта из инкогнито и через мобильную сеть. Убедиться, что публичный API также доступен.
8. Прикрепить отчёт и указать ссылку в Яндекс Форме. Проверить вложение и адрес перед отправкой; саму отправку пользователь выполняет отдельно.

Презентация и Figma не являются явными требованиями приведённого задания. Дополнительные правила конкурса проверяются перед сдачей. На период оценки сохраняются публичный адрес, опубликованные версии данных и работоспособность backend.

**Демонстрация, 2–3 минуты:** регион и ДТ → динамика за 12 недель → сравнение на общей дате → заправка нескольких машин → цена поставщика → дата, источник и статус обновления. Отдельно для технической проверки: журнал автоматического сбора и явно обозначенный резерв.

**Критерий готовности:** сценарий проходит без объяснений разработчика; каждая цена проверяется; расчёт воспроизводится; выполнены P0, FR-01–FR-24 и AC-01–AC-36; реально проверены развёртывание, таймер, резерв и совместная работа с VPN. Целевые и измеренные результаты в отчёте разделены.
